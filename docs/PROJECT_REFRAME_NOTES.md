# Project Audit and Reframe Notes

Date: 2026-06-12
Repository: `Shi0v0Jasmine/GE5226_WHERE-TO-DINE-DEMO`

## 1. What the project was originally trying to do

The original project idea was a WebGIS restaurant recommendation system for NYC:

- Use restaurant POIs from Google Maps and OpenStreetMap to identify dense dining zones.
- Use NYC TLC taxi drop-offs during dining hours as a revealed-preference signal: people "vote with their feet" by traveling to dining areas.
- Cluster restaurant points and taxi drop-off points with HDBSCAN.
- Intersect restaurant clusters with taxi activity clusters to produce final dining hotspots.
- Rank hotspots with a weighted score combining popularity and accessibility.
- Eventually support multi-modal accessibility through walking/driving/transit isochrones.
- Serve the result through a Flask + Leaflet web demo.

In short: it was framed as "objective dining hotspot discovery from mobility data", not just another review-based ranking app.

## 2. What is actually implemented now

Implemented:

- Data merge for Google Maps and OSM restaurants.
- HDBSCAN clustering for restaurants.
- Taxi data filtering, temporal weighting, and clustering.
- Spatial intersection between dining zones and taxi hotspots.
- A Flask web demo showing final hotspots and returning nearby recommendations.

Partially implemented or only documented:

- Isochrone/accessibility analysis exists as a standalone module, but it is not wired into the web recommendation flow.
- Transit/GTFS routing is documented in the plan but not implemented end to end.
- Validation, sensitivity analysis, and robust scoring are mostly described in docs rather than implemented.

Current demo recommendation behavior:

- User clicks a location.
- The app measures Euclidean distance to hotspot centroids.
- It filters by a radius in km.
- It calculates `recommendation_score = 0.6 * popularity_score + 0.4 * accessibility_score`.

This is useful for a demo, but it is not yet a true travel-time-aware recommendation engine.

## 3. Key data issue: taxi trips do not have point coordinates

The local 2024 NYC yellow taxi parquet files were checked with `pyarrow`. They include:

- `PULocationID`
- `DOLocationID`
- pickup/dropoff timestamps
- fares and trip metadata

They do not include raw pickup/dropoff latitude and longitude.

The current pipeline handles this by joining `DOLocationID` to the taxi zone shapefile and assigning each trip to the taxi zone centroid. That means the taxi layer is not precise point-level foot traffic. It is zone-level demand collapsed to centroids.

Implication:

- The project can identify broad high-demand dining districts.
- It cannot reliably infer the exact street corner, restaurant block, or "which restaurant is good" from taxi data alone.
- Many trips in the same taxi zone become identical or near-identical spatial signals, which can make clustering and ranking look more precise than the data supports.

This should become an explicit limitation and a design constraint, not a hidden weakness.

## 4. Scoring issues to revisit

The current pipeline normalizes restaurant density and taxi density by dividing by the maximum value in the current hotspot set. That produces scores in `[0, 100]`, but it is sensitive to outliers and changes whenever the candidate set changes.

The web app's accessibility score is also local to the filtered result set:

```python
accessibility_score = 100 * (1 - distance_km / max_dist)
```

This means the same hotspot can receive a different accessibility score depending on which other hotspots were nearby in that request. It is convenient for a demo, but not stable as a product metric.

Recommended scoring upgrades:

- Use log or percentile normalization for skewed demand features.
- Use a stable denominator for accessibility, such as selected max travel time or radius.
- Add deterministic tie-breakers: travel time, rating confidence, review count, restaurant diversity, recency.
- Separate "area popularity" from "venue quality".
- Use Bayesian/Wilson-style rating confidence if review data is included.
- Make user preference weights explicit: popular, nearby, hidden gem, local favorite, late-night, budget, cuisine-specific.

## 5. Output reproducibility issue

Current `data/processed` outputs are not fully synchronized:

- `final_hotspots.geojson` contains 14 final hotspot features.
- `intersection_analysis.json` reports 0 final hotspots.

This suggests the current processed files were generated by different runs or manual edits. Before presenting this as a portfolio project, the pipeline should be made reproducible from raw/interim inputs, or the repo should clearly separate demo fixtures from generated outputs.

## 6. Inspiration from 高德扫街榜

Public descriptions of 高德扫街榜 suggest the key idea is not "reviews only", but ranking local places using real-world behavior plus trust signals:

- Behavior signals: search, navigation, arrival, repeat visits, special trips, collections/favorites.
- Trust signals: credit-weighted or credibility-weighted feedback and AI risk control to reduce fake reviews/noise.
- Dynamic lists: daily updates, seasonal/time-aware lists, category-specific lists, local-specialty lists.
- Spatial intelligence: recommendations tied to where the user is, what they are doing, and what is reachable.

## 7. Recommended reframe for the portfolio version

A stronger and more honest framing:

> Build an urban dining discovery system that ranks NYC dining areas using real-world mobility demand, POI quality, and accessibility, while explicitly modeling uncertainty caused by zone-level taxi data.

Possible product name:

- StreetRank NYC
- NYC Dining Pulse
- Where to DINE: Urban Dining Intelligence

Positioning:

- Not "we know exactly where the best restaurant is from taxi data".
- Instead: "we identify high-confidence dining districts and explain why they are attractive: density, demand, quality, diversity, and accessibility."

Resume-friendly story:

- Built an end-to-end geospatial analytics pipeline from 28M+ dining-hour taxi drop-offs and 20K+ restaurant POIs.
- Diagnosed spatial-resolution limits in public mobility data and redesigned scoring around uncertainty-aware district ranking.
- Implemented HDBSCAN hotspot detection, geospatial joins, temporal weighting, and an interactive WebGIS demo.
- Planned/implemented robust normalization, reproducible data pipeline, and accessibility-aware recommendation APIs.
